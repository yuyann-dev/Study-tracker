# 刷题模式（exercise / 习题册）排期逻辑盘查

> 盘查范围：`frontend/js/app.js`（12895 行）、`frontend/index.html`、`frontend/css/style.css`
> 盘查日期：2026-10-05
> 盘查方式：只读代码，不改任何逻辑。错题本（mistake）已优化代码保持原样，仅作对照。
> 核心结论先行：**exercise 根本不走"条目式间隔排期"，它是一个"剩余量 ÷ 剩余学习日"的纯进度推进模型。** 错题本那套（due 队列、spread、舒适量、容量、pullForward、ensureOne、retention、临考策略条）对 exercise 几乎全部直接 early-return 或返回空。

---

## 0. 一句话总览

| 维度 | mistake（错题本） | exercise（刷题） |
|---|---|---|
| 进度单位 | 一条条 item（道） | 页码区间合并 / 套卷完成度 |
| 是否有 due 队列 | 有，按 nextReviewDate 排 | **没有，items 恒为空数组** |
| 每日目标来源 | due 条数（硬） | `剩余量 ÷ 剩余学习日`（**软建议**） |
| 每日硬上限 | min(舒适量, 容量, 到期均摊) | **无硬上限** |
| 间隔表 / stage / interval | 有，评分驱动 | **字段在但从不读取** |
| 过期 banner / 归档入口 | 有 | **被隐藏 → exercise 无法归档** |
| 临考策略条 / 后置 / 暂停新收录 | 有 | **全部 early-return** |

### 2.9 exercise 真正在用的"排期"：`getMetrics`（app.js:1812）

这是 exercise 排期的**唯一真实引擎**。核心：

```js
// app.js:1838-1844
m.total       = exercise ? 页/套范围并集 : ...;
m.currentPage = getCompletedPages(p);                 // 页区间合并 / 套卷加权
m.remaining   = Math.max(0, m.total - m.currentPage);
m.daysLeft    = m.deadline ? diffDays(today, deadline) : null;
m.daysAvailable = (m.daysLeft!=null && m.startDate)
  ? Math.max(0, m.daysLeft + 1 - 已度过的非学习日) : m.daysLeft;
m.needPerDay  = m.daysAvailable > 0 ? m.remaining / m.daysAvailable : Infinity;
```

学习日产能估计（app.js:1903 附近，`activityPerDay × perStudyDayRaw`）：
- `activityPerDay`：贝叶斯先验≈每周 5 天，从历史 records 学习日比例后验。
- `perStudyDayRaw`：近 14 天 EWMA，学习日当天平均完成量。
- `perStudyDay` = `remaining / (剩余自然日 × activityPerDay)`，再乘 catch-up 系数。

`getDailyTarget`（app.js:4185）+ `getCatchUpPlan`（app.js:4128）与背书普通窗口共用：
```js
// app.js:4128
function getCatchUpPlan(p, m) {
  const remaining=m.remaining, daysAvailable=m.daysAvailable;
  if (!(remaining>0 && daysAvailable>0)) return out;   // ★ 过期(daysAvailable<=0)时返回空 plan
  ... onTime / delay 两套最省力按期方案 ...
}
```

> 结论：exercise 的"排期"= 剩余多少 ÷ 还剩几个学习日 = 今天建议做多少。**它是一个会随进度自动追赶的均摊数，不是一个被容量/舒适量约束的队列。**

## 3. 舒适量与容量

### 3.1 各函数对 exercise 的返回

```js
// app.js:2579
function defaultComfortCap(p) {
  if (p.type === 'recite') return 6;
  return 10;                       // ★ exercise=10（与 mistake 默认同值）
}
// app.js:2584  getComfortCap 读 p.spreadThreshold，缺省回退 defaultComfortCap → exercise=10
// app.js:2591  getComfortAdvice  → if(p.type==='exercise') return null
// app.js:2608  renderComfortAdvice → exercise 直接 hide
```

### 3.2 关键事实

- **exercise 的 `spreadThreshold` 默认 10，但设置页不暴露、也从代码不读取来排任何东西。**
  - 设置页隐藏：`openSettings`（app.js:9489-9496）`spreadSection` 对 exercise 隐藏；提交时 `submitSettings`（app.js:11724）`if (p.type!=='exercise') spreadThreshold=...` 跳过。
- **exercise 的 `dailyCapacity` 恒为 null，设置页也不暴露。**
  - `openSettings`：`capacitySettings`（9440-9441）只对 `canReviewMode`（mistake/recite）显示。
- **"实际排题上限 = min(舒适量, 容量)" 对 exercise 完全不生效**——因为 exercise 没有待排队列，`getDailyCapacity` 算出的 5 / `getComfortCap` 10 都不参与任何裁剪。
- exercise **没有**独立的舒适量建议函数（`getComfortAdvice` 直接返回 null）。

> 这意味着：用户某天刷 50 页、100 页，系统不会有任何"超量/舒适量"提示。每日目标纯软建议。

## 4. 新题收录与刷题进度

### 4.1 新题/新页如何进入

exercise **没有"新题"实体**。进度通过打卡 records 累加：
- 页模式：`btnCheckin`（app.js:12171）提交 `{startPage, endPage}`。
- 套卷模式：`btnSetCheckin`（app.js:12141）提交整套 / 按板块 pct / done-q。

页码进度由区间合并得到（`getBookDoneRanges` → `countRanges`，app.js:1776-1798），重复录入自动去重/覆盖。

### 4.2 进度统计

- 已做：`getCompletedPages`（app.js:1772）——页=合并区间数；套=`getCompletedSets` 加权（app.js:1768）。
- 未做：`total - currentPage`。
- **"已掌握"：exercise 没有 per-question 的 isMastered。** "完成"= `remaining===0`（整本刷完）。
- 套卷板块加权：`getNormalizedSections`（app.js:1706）权重自动归一化。

### 4.3 做错的题进错题本？——**不自动，全靠手动关联**

关联是**单向、手动**的：

```js
// app.js:10853  openLinkedMistakes
// 关联存在于 mistake 项目上：m.refProjectId === exercise.id
// app.js:4019  getRefUnitProgress：从关联刷题本借结构/进度
```

- 用户在刷题本页点「🔗 关联错题本」(`btnLinkedMistakes`) → 手动创建一个 linked mistake 项目（`btnCreateLinkedMistake` / `btnCreateLinkedFromList`）。
- 创建时用刷题本的 units/paperSections 对齐结构（`structuresMatch` / `applyRefStructure`），**但题目本身要用户在错题本里一条条手动收录。**
- 刷题本侧只是显示"🔗 N个关联错题本"（app.js:7640）。

> **没有任何"刷题做错 → 自动写进错题本"的联动。** 关联机制只是结构对齐 + 进度展示，不是数据同步。

## 6. 过期与截止日处理

### 6.1 过期后各机制行为

| 机制 | exercise 过期后 |
|---|---|
| `getMetrics` | `daysLeft<0`，`daysAvailable<=0`，`needPerDay=Infinity`，`hasDeadline=false`（app.js:2005） |
| `perStudyDay` | 因 `hasDeadline=false` → **保持 null**（无均摊目标） |
| `getDailyTarget` | per=null → 退回 needPerDay（Infinity，被渲染层兜成"未设目标"） |
| `getCatchUpPlan` | `if(!(remaining>0 && daysAvailable>0)) return out` → **onTime/delay 全空**（app.js:4137） |
| 过期横幅 | **隐藏**（app.js:5830） |
| `rebalanceExpiredItems` | items=0 → return 0 |
| 归档按钮 | **无处可达**（见 §8 P1-1） |

### 6.2 过期状态卡文案（app.js:4547 分支 5）

```js
// app.js:4547
if (m.daysLeft < 0) {
  title = '已经过了原定目标日';
```

**结果：文案承诺"一起重新理顺"，却没有任何可执行方案或按钮。** 用户被引导到"重新规划"，但 UI 上没有重设目标/归档/继续不赶进度的入口（那些按钮在被隐藏的过期横幅里）。

### 6.3 与 mistake 过期的差异

- mistake 过期有完整闭环：过期横幅 → 归档 / 重设目标日 / 继续不赶进度 / 一键后移（app.js:5870-5911）。
- exercise 过期：只剩一句干巴巴的状态卡文案 + 一个空 plan。**用户只能自己摸进设置改 deadline。**

## 7. 模式差异（balanced / classic / gentle）

- **balanced（均匀错峰）vs classic（经典间隔）**：对 exercise **无意义**。`reviewMode` 设置页对 exercise 隐藏，新建写死 `'classic'`（app.js:11105），且 balanced 分支全部 `p.type!=='exercise'` 门控（app.js:3106、2428、2616、5963）。exercise 没有队列，无所谓错峰。
- **gentle（温和模式）**：不是 reviewMode，而是 `excessBanner.dataset.mode='gentle'`（app.js:6399-6402、12732）的一个**UI 状态**，用于"今天做了不少但还有剩"的软提示。该 banner 本身对 exercise 隐藏（app.js:5945），所以 **exercise 没有 gentle**。

> exercise 本质上只有一种"模式"：按 deadline 均摊的软目标。它不存在间隔模式之分。

- 该横幅对 exercise 直接 hide（app.js:5830）。
- 项目列表 `renderProjectList` 对活动项目只有「删除 ×」（app.js:7653），对已归档项目才有「取消归档」（7675）。
- **后果：一个做完/弃用的刷题本，用户只能彻底删除，无法像错题本那样归档收纳。** 与 v3"归档收纳箱"设计（app.js:7588-7678）脱节。

**P1-2　exercise 过期后是"死路"——承诺重新规划却无任何操作入口**
- 状态卡说"一起把计划重新理顺"（app.js:4549），但 `getCatchUpPlan` 在 `daysAvailable<=0` 时返回空 plan（app.js:4137），后续 onTime/delay 方案全被跳过。
- 过期横幅（重设目标 / 归档 / 继续不赶进度）对 exercise 隐藏。
- **后果：过期刷题本没有"一键重设目标日 / 归档 / 延期"的引导，用户只能手动进设置改 deadline。**

### P2 — 设计残留 / 死数据 / 体验缺口

**P2-1　僵尸字段：intervals / reviewMode='classic' / spreadThreshold=10 / dailyCapacity=null 被写入但从不使用**
- 迁移（app.js:1059-1065）和新建（app.js:11098、11105-11109）给 exercise 塞了这些字段，但 exercise 没有 item、不排期。
- **风险：后续维护者极易误以为 exercise 有间隔/舒适量体系，在这些字段上"做文章"，结果改了不生效。** 建议在文档/代码注释中标注 exercise 不消费这些字段。

**P2-2　`getDailyCapacity` / `getStudyDayRatio` / `getBacklogCatchUp` 对 exercise 是死代码**
- `getDailyCapacity`（app.js:2695）仍对 exercise 走一遍 EWMA 冷启动计算（得到 ~5），但结果无人消费（舒适量建议隐藏、压力板仅 mistake、spread 无 item）。
- 不是 bug，但属于每次 render 都白跑的开销，且易误导。

**P2-3　exercise 无任何每日硬上限 / 超量提示**
- 每日目标纯软建议，刷多少都不提示（app.js:5288-5296 超量只给 coach 文案，不阻断）。
- 这是设计选择，但与错题本"min(舒适量,容量)"体系完全脱节。**若要给刷题本加"别一次刷爆"的提示，目前没有任何钩子。**

**P2-4　exercise 无临考策略 / 战略性后置 / 暂停新收录**
- `tightStrategyBar`、`tacticalPostpone`、`pauseNewCollection` 全部 mistake-only（app.js:6079 等）。
- 临考刷题本只能靠状态卡文案，没有"暂停新页、优先补关联错题"之类的策略。

**P2-5　做错的题不进错题本（无自动联动）**
- 关联是纯手动 + 结构对齐（app.js:10853），不是数据同步。
- 这可能是有意设计，但用户心智上"刷题→错题进错题本"的预期落差值得在 UI 提示。

### P0 — 无

未发现导致数据错乱或崩溃的 P0 级 bug。exercise 作为进度推进器自洽运行。

## 10. 与错题本（mistake）对比 & 可复用性评估

| 错题本已优化的能力 | 能否直接复用到 exercise | 说明 |
|---|---|---|
| due 队列 / nextReviewDate 排期 | ❌ 不能直接用 | exercise 无 item，模型不同 |
| balanced 错峰 | ❌ | 无队列，错峰无对象 |
| 舒适量/容量 min() 硬上限 | ⚠️ 概念可借鉴，代码不能直接套 | exercise 目前无队列上限；若要加"每日建议上限"需独立设计 |
| 过期 banner（重设目标/归档/继续不赶进度） | ✅ **强烈建议复用** | 当前对 exercise 隐藏，是 P1-1/P1-2 的根因 |
| 归档收纳箱 | ✅ 建议开放给 exercise | 列表已有 unarchive 闭环，只差把 archive 按钮暴露给 exercise |
| pullForward / ensureOne / retention | ❌ | 无 item，不适用 |
| getCatchUpPlan 最省力按期方案 | ⚠️ 可复用但需修过期分支 | 过期时应给出"重设目标日"建议而非返回空 |
| 临考策略条 / 后置 / 暂停新收录 | ⚠️ 概念可借鉴 | exercise 的"新收录"=新页，可设计"临考暂停新页、优先补关联错题" |
| 弱点板 | ❌ | exercise 无题条目，无弱点可析 |

### 落地建议（不改代码，仅给方向）

1. **P1-1/P1-2 一起修**：把 `deadlinePassedBanner` 对 exercise 的隐藏（app.js:5830）放开，但按 exercise 定制按钮（归档 + 重设目标日，去掉"继续不赶进度/一键后移"这类队列语义按钮）。
2. 过期时 `getCatchUpPlan`（app.js:4137）对 exercise 返回空 plan 的问题：可在状态卡分支 5（app.js:4547）补一句"可在设置里把目标日往后调"并接按钮。
3. 清理/标注僵尸字段：在 `migrateProject`（app.js:348）对 exercise 的分支加注释，说明 intervals/reviewMode/spreadThreshold 不被消费，避免后续误改。
4. 若希望刷题本也有"别一次刷爆"的体验，需独立设计一个**软舒适量提示**（类似 recite 的 overSmall coach 文案），而非套用错题本的队列硬上限。
