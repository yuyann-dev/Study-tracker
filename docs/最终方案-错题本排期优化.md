## 二、BUG修复清单（P0必须修复）

### BUG-01：scheduleNextReview 过期clamp制造新逾期

| 项目 | 内容 |
|------|------|
| **根因** | app.js:3132（balanced）和3135（classic）执行 `if (p.deadline && d > p.deadline) d = p.deadline`，未判断deadline是否已过期。过期后（deadline < today），新间隔排到的未来日期 d > 过去的deadline → 被clamp回过去 → 该题立刻变新逾期 → 用户再做 → 再clamp → 死循环 |
| **影响范围** | 所有有deadline且已过期的错题本/背书项目；balanced和classic两种模式都中招；新收录题也中招（新题首次复习日被clamp到过去） |
| **用户证据** | 已过期用户模拟痛点1："我明明刚点了做对了，系统不是说下次7天后吗？怎么今天又出现在逾期列表里？我连续做了三道，三道全回来了。" |
| **修复方案** | clamp前增加 `p.deadline >= todayStr()` 条件： |

```js
// app.js:3132 修复前：
if (p.deadline && d > p.deadline) d = p.deadline;
// 修复后：
if (p.deadline && p.deadline >= todayStr() && d > p.deadline) d = p.deadline;

// app.js:3135 修复前：
if (p.deadline && base > p.deadline) return p.deadline;
// 修复后：
if (p.deadline && p.deadline >= todayStr() && base > p.deadline) return p.deadline;
```

| **配套处理** | 修复后，已被错误clamp到过去日期的存量题：不做自动迁移（避免大规模改数据），但方案C的"修改截止日"按钮点击后触发一次 `rebalanceOverdueAfterDeadlineChange()`（新增函数），把 nextReviewDate < today 且 item 不在锁死名单的题重新摊到未来 |
| **验证标准** | 过期项目复习一道good题 → 刷新 → 该题不出现在逾期列表 → 下次复习日是正常间隔后的未来日期 |

## 三、方案A最终设计：容量/舒适量建议

### 3.1 核心算法：smartCap来源拆解 + 多维度联合判断

**为什么需要来源拆解？** —— 来自截止日偏紧用户模拟的关键发现：smartCap高有三种原因，对应三种完全不同的建议方向。

```
getDailyCapacity(p, today) 的四个来源：
  EWMA节奏容量      = getActivityCountsByDate EWMA（含新学，半衰期14天）
  backlogCatchUp    = getBacklogCatchUp.need（积压追赶）
  deadlineLevelCap  = getDeadlineLevelCap.cap（按期均摊）
  weekdayAwareCap   = getWeekdayAwareCap（星期画像，只上抬不下降）

smartCap = max(四个来源)

来源拆解逻辑：
  计算四个来源各自的值，找出最大值是哪一个。
  如果 deadlineLevelCap > EWMA 且 deadlineLevelCap > backlogCatchUp：
    → 压力来源 = 截止日太近（不是用户节奏快）
    → 建议方向 = 后移截止日（见方案C偏紧阶段），不建议调高舒适量
  如果 EWMA > comfort 且 EWMA > deadlineLevelCap：
    → 压力来源 = 用户实际节奏快于舒适量设定
    → 建议方向 = 调高舒适量（方案A-情况1）
  如果 backlogCatchUp > comfort 且 backlogCatchUp 是主导：
    → 压力来源 = 历史积压
    → 建议方向 = "稳步清积压即可"，不建议调高也不建议调低
```

**新增函数 `getSmartCapSource(p, date)`**（建议放在 app.js:2760 附近，紧跟 getDailyCapacity 之后）：
```js
function getSmartCapSource(p, date) {
  const ewma = getEwmRate(p, date);           // 从getDailyCapacity中拆出
  const backlog = getBacklogCatchUp(p).need;   // 已有
  const dlCap = getDeadlineLevelCap(p, date).cap; // 已有
  const weekday = getWeekdayAwareCap(p, date); // 已有
  const sources = { ewma, backlog, deadline: dlCap, weekday };
  const maxVal = Math.max(...Object.values(sources));
  const maxKey = Object.keys(sources).find(k => sources[k] === maxVal);
  return { source: maxKey, value: maxVal, all: sources };
}
```

### 3.2 建议算法：调高档（智能模式，smartCap来源=EWMA）

**触发条件（全部满足）：**
1. `p.type === 'mistake'`（本期只做错题，背书后续扩展）
2. `p.dailyCapacity == null`（智能模式）
3. `p.deadline >= todayStr()`（deadline在未来才需要赶进度）
4. `smartCapSource.source === 'ewma'`（EWMA是smartCap的主导来源，排除deadline均摊导致的高smartCap）
5. `smartCap > comfort`（系统认为你能做更多，舒适量是瓶颈）
6. `feasibility.level !== 'risk'`（risk交给mistakeRiskBanner+后移deadline建议）
7. **距deadline > 30天**（临考期不弹"调高舒适量"，避免增压——来自临考积压用户需求1）
8. 当天尚未弹过（`p.excessAdviceShownDate !== todayStr()`）
9. **连续低迷天数 < 21天**（冲刺期短期低迷用户保护——来自冲刺期用户红线）

**建议值计算：**
```js
const ewmaRate = smartCapSource.value;  // EWMA实际速率
const suggest = Math.max(
  defaultComfortCap(p),        // 下限保护：不低于默认值10
  Math.min(ewmaRate, 25)       // 上限放宽到25（原方案卡20，高强度用户痛点3要求放宽）
);
// 额外保护：如果历史P75 < suggest，取P75
const p75 = getHistoricalP75(p, 60);  // 新增：近60天日均完成P75
const finalSuggest = Math.min(suggest, Math.max(p75, defaultComfortCap(p)));
```

**新增辅助函数 `getConsecutiveLowDays(p)`**：
- 从今天往回数，连续多少天的完成量 < 历史P75 × 0.6
- >21天才允许考虑"真实低产能"判断（但本期仍不主动建议调低，见决策点D2）

### 3.3 建议算法：积压说明档（智能模式，smartCap来源=backlog或deadline）

当 `smartCap > comfort` 但 smartCap 来源是 backlogCatchUp 或 deadlineLevelCap 时：
- **不建议调高舒适量**
- 显示中性说明行："今天的量主要来自历史积压 / 截止日追赶，稳步清完即可。"
- 配一个 ✕ 关闭按钮

### 3.4 建议算法：固定模式配置矛盾档

**触发条件（全部满足）：**
1. `p.dailyCapacity != null`（固定模式）
2. `p.dailyCapacity > comfort`（存在配置矛盾：设了大容量但舒适量是瓶颈）
3. 连续 ≥3天 实际排题量 = comfort（即系统一直被舒适量卡住，不是题不够）
4. 当天尚未弹过（复用 `p.excessAdviceShownDate`）
5. **距deadline > 30天**（临考期走"考前加速"分支）

**文案（二选一，给用户决策权）：**
```
💡 你设置的每日容量是 {capacity} 条，但舒适量 {comfort} 会把每天排题压到 {comfort} 条。
   最近几天系统一直按 {comfort} 条在排。
   
   [ ] 我确实能做 {capacity} 条 → 把舒适量调到 {capacity}
   [ ] {comfort} 条就够了 → 把每日容量改成 {comfort}
   [✕] 先不管
```

**一键应用行为：**
- 选"调高舒适量"：`p.spreadThreshold = p.dailyCapacity`
- 选"调低容量"：`p.dailyCapacity = comfort`
- 两者都立即 saveStore() + render()，当天不再弹

### 3.5 建议算法：固定模式考前加速档

**触发条件：**
1. 固定模式（`p.dailyCapacity != null`）
2. 距 deadline ≤ 30天
3. feasibility.level === 'risk'（按当前固定容量确实清不完）
4. 当天尚未弹过

**文案：**
```
⚠️ 距考试还有 {daysLeft} 天，按当前每天 {capacity} 条的节奏，预计还剩 {backlog} 条来不及刷完。
   固定模式不会自动加量。
   
   [ ] 最后 {daysLeft} 天临时调到 {suggestCap} 条/天（考完自动恢复 {capacity}）
   [ ] 永久调高舒适量到 {suggestCap}
   [ ] 不调整，我自己控制
```

**临时加量实现**：新增 `p.sprintCap = suggestCap` 和 `p.sprintEndDate = deadline`。`getSpreadDayCap` 中固定模式分支增加判断：如果今天在 sprintEndDate 内，用 `min(comfort, sprintCap)` 替代 `min(comfort, dailyCapacity)`。

### 3.6 弹出频率控制

```
每天最多弹1次（用 p.excessAdviceShownDate = todayStr() 记录）
点✕或一键应用 → 当天不再弹
第二天满足条件 → 可再弹（但文案/建议值可能因数据变化而不同）

降频机制（来自低强度用户和固定容量低用户的反馈）：
  如果用户连续3天点✕关闭同一类建议 → 写入 p.excessAdviceDismissCount
  dismissCount >= 3 → 切换为"每周一弹"模式（每周一第一次打开时评估一次）
  用户点了一键应用后 → dismissCount清零
```

### 4.4 偏紧但未过期阶段：后移截止日建议

**这是对方案C的重要扩展**——来自截止日偏紧用户模拟的核心发现：最痛的不是"已经过期"，而是"还没过期但已经被压了一个月"。

**触发条件：**
1. `feasibility.level === 'risk'` 或 `'tight'`
2. `smartCapSource.source === 'deadline'`（压力来源是截止日均摊，不是EWMA）
3. 当天尚未弹过（复用一个新字段 `p.deadlineTightWarnDate`）
4. 距deadline > 0（还没过期）

**建议日期计算**：
```js
// 找到一个后移日期，使得每天工作量回落到舒适量以内
// 目标：studyDays × comfort ≈ totalWork
const totalWork = remainRounds + predictedNew;  // 已有
const targetDaily = comfort;  // 用户舒适量
const neededDays = Math.ceil(totalWork / targetDaily);
const suggestedDate = addDays(today, neededDays);
// 如果 suggestedDate - deadline > 14天，才值得建议后移（否则差距太小不值得动）
```

**文案（琥珀色，非红色）：**
```
💡 你给这本设的目标是 {deadline}。按目前进度，把目标调整到 {suggestedDate} 的话，每天可以少做 {gap} 条，压力会小很多。

```

**频率：**
- feasibility刚进入risk/tight当天：弹第一次
- 用户点"保持deadline"：7天内不再就同一项目建议后移
- 用户真的后移了：永久不再弹（除非新的risk出现）
- 连续7天risk未处理：每周最多再弹1次

## 五、排期算法优化清单

### 算法-01：scheduleNextReview clamp修复
→ 已在BUG-01详述。过期后不再clamp到过去deadline。

### 算法-02：超量横幅是否需要看容量？
→ **需要**。已在BUG-02详述。横幅必须读 `getDailyCapacity`，区分"系统计划内的量"和"真积压"。

### 算法-03：固定容量模式是否需要按期均摊兜底？
**结论：需要，但以"提示+临时加量"方式，不自动改固定值。**

**根因**：固定模式下 `getSpreadDayCap`（app.js:2670-2687）直接返回 `min(comfort, dailyCapacity)`，完全旁路了 `getDeadlineLevelCap`、`getBacklogCatchUp`、`getMistakeDayPlan.target`。导致考前无法自动加量（固定容量低/高用户共同痛点）。

**方案**：不改变固定模式的排题行为（用户选固定就是要确定性），但：
1. 临近截止日（≤30天）且 feasibility=risk 时，弹"考前临时加量"建议（见3.5节）
2. 新增 `p.sprintCap` + `p.sprintEndDate` 机制，用户同意后临时覆盖
3. 设置页固定容量选项旁加一行说明："选固定容量后，系统不会在考前自动加量。如需考前冲刺，可以随时调高或切换为智能模式。"

### 算法-04：今天/未来排题口径统一

**问题**：今天排题 = `max(comfort, getDailyCapacity)` 可能=23；未来错题 = `getMistakeDayPlan.target = min(hardMax=15, raw=23)` = 15。前后不一致，导致前松后紧（高强度用户痛点7）。

**根因**：`hardMax = min(20, max(12, comfort×1.5))`（app.js:3280）用comfort算上限，但今天的 `getDailyCapacity` 不受这个hardMax约束。

**方案**：
```
修改 getMistakeDayPlan.hardMax 计算（app.js:3257附近）：
  旧：hardMax = min(20, max(12, comfort × 1.5))
  新：hardMax = min(25, max(12, Math.max(comfort × 1.5, ewmaRate)))
  
  即：hardMax 取 comfort×1.5 和 EWMA实际速率 的较大值。
  高强度用户EWMA=18 → hardMax=18（而不是15）
  普通用户EWMA=10 → hardMax=15（不变）
```

**效果**：未来每天目标量跟随用户实际速率，不再被comfort×1.5卡死。均摊曲线老实——需要多少排多少，上限是用户真实能力。

### 算法-05：可行性警告基准改用EWMA

**问题**：`getMistakeFeasibility`（app.js:3264-3285）用comfort和comfort×1.5判断tight/risk，高强度用户被误报（高强度用户痛点4）。

**方案**：
```
修改判定基准：
  comfort = getComfortCap(p)
  ewmaRate = getEwmRate(p)  // 新增提取
  effectiveComfort = Math.max(comfort, ewmaRate)  // 取较大值
  hardMax = min(25, max(12, effectiveComfort × 1.5))
  
  risk: work > studyDays × hardMax
  tight: work > studyDays × effectiveComfort
```

**效果**：高强度用户EWMA=18 → effectiveComfort=18 → 判定按18条/天算，不再用默认值10误报。

### 算法-06：pullForward透明度

**问题**：系统从未来14天提前拉题到今天，用户完全不知道（高强度用户痛点9、低强度用户痛点7、固定容量高用户痛点6）。

**方案**：
1. 被pullForward拉到今天的题，题目行加一个小标签 `⚡提前`（灰色小字）
2. 悬停显示tooltip："原定于 {originalDate} 复习，系统为赶进度提前到今天"
3. 今天列表顶部加一行小灰字（仅当pullForward实际拉了题时）：
   "今天从未来提前安排了 {N} 道题帮你减轻后面压力"

**实现位置**：`pullForwardIfNeeded`（app.js:3289）拉题后记录 `p.lastPullForwardCount = N` 和 `p.lastPullForwardDate = today`。renderReview时如果 `p.lastPullForwardDate === today` 且 N>0，显示提示行。

### 算法-07：earlyReviewed惩罚调整

**问题**：`scheduleNextReview` line 3080 `if (item.earlyReviewed) gap = round(gap * 0.85)`，一刀切缩短间隔，惩罚主动加量的用户（高强度用户痛点8）。

**方案**：
```js
// 修改前：
if (item.earlyReviewed) gap = Math.round(gap * 0.85);

// 修改后：
if (item.earlyReviewed && lastRating !== 'good') gap = Math.round(gap * 0.85);
// 即：提前复习 + 评价"记得/good" → 不缩短间隔
//     提前复习 + 评价"模糊/忘记" → 仍缩短（说明确实需要多巩固）
```

**实现**：在 `transitionReview`（app.js:3413）中记录本次评价到 `item.lastRating = rating`，scheduleNextReview时读取。

### 算法-08：逾期处理是否需要自动顺延？

**现状**：逾期题堆在今天列表最顶部，用户做不完就滚存到明天，越积越多（低强度用户痛点5、固定容量高用户痛点4）。

**方案**：不做"自动顺延"（会改变题目的复习日期，干扰间隔算法），而是：
1. **"今天就到这"按钮**：在复习列表底部加一个小按钮，点击后：
   - 将今天未做完的条目中，非锁死项（`canBeSpread=true`）自动走一次 `spreadItems` 摊到未来3天
   - 文案："今天没做完的已帮你排到这周内"
2. 这个按钮是**用户主动触发**的，不是系统自动的（避免系统擅自改用户计划）
3. 位置：复习列表底部，灰色小字按钮

### 算法-09：新题收录速度预测 & 剩余轮次计算
**现状评估**：`getMistakeCollectRate`（line 3231）和 `remainRounds`（line 3272）算法本身正确，问题在于feasibility用comfort而非EWMA作为基准（已在算法-05修复）。新题收录突然爆发的场景（高强度用户7.6）暂不处理，记录为后续迭代。

### 算法-10：均匀分布 vs 经典间隔模式说明
**方案**：设置页两个模式选项之间，加一段说明文字（大白话）：
```
均匀分布：系统帮你把每天的复习量摊平，临近考试自动加量追赶。推荐大多数用户。
经典间隔：严格按记忆曲线，到期多少做多少，不自动调整节奏。适合喜欢确定性的用户。
```
不改变算法本身，只改善设置页可理解性（来自所有8个用户的共同反馈："不知道自己在用哪种模式"）。

## 九、需要用户拍板的关键决策点

以下决策在8份用户模拟中出现了明确分歧，需要最终确认：

### 决策点D1：低强度用户是否允许建议调低舒适量？

| 选项 | 内容 | 依据 |
|------|------|------|
| **维持产品决策（推荐）** | 不主动建议调低舒适量，最低不低于默认值10。通过"今天就到这"按钮+中性横幅+不评判措辞缓解低强度用户焦虑。 | 已批准决策"方案B已否决"+"不要建议低于10" |
| 放宽限制 | 当连续21天以上完成量<comfort×0.7且backlog稳定时，允许建议调低到 `max(5, round(EWMA))` | 低强度用户模拟痛点4强烈要求；但风险是可能把用户"锁死"在低产能 |

**推荐：维持产品决策**。理由：①产品决策已明确否决 ②低强度用户的核心痛点是"清单太长+被评判"，不是"舒适量太高"——通过中性化横幅+体面收尾按钮即可缓解 ③调低舒适量可能让用户彻底放弃复习。

### 决策点D2：固定模式是否纳入方案A建议范围？

| 选项 | 内容 | 依据 |
|------|------|------|
| **纳入（推荐）** | 固定模式增加"配置矛盾检测"分支（3.4节）和"考前加速"分支（3.5节） | 固定容量低/高用户模拟都强烈要求；原方案"固定模式不弹建议"会漏掉最需要校准的用户 |
| 不纳入 | 固定模式永远不弹建议，用户自己去设置页调 | 原方案设计；但固定容量高用户会继续困惑"为什么我设了20只排10" |

**推荐：纳入**。理由：固定模式用户恰恰是"拍脑袋设了数字、需要系统帮我校准"的人，完全不弹建议等于放任误解。

### 决策点D3：smartCap来源拆解——deadline主导时是否转建议后移截止日？

| 选项 | 内容 | 依据 |
|------|------|------|
| **是（推荐）** | smartCap高的原因是deadline均摊时，不建议调高舒适量，转而建议后移截止日 | 截止日偏紧用户模拟核心发现：方案A原设计会把这类用户往错的方向推（建议调高舒适量=让他们每天做更多=更痛苦） |
| 否 | 不管smartCap来源，只要smartCap>comfort就建议调高舒适量 | 原方案设计；但会误导截止日设早了的用户 |

**推荐：是**。这是8份用户模拟中最有价值的算法改进——区分"你节奏快所以舒适量偏低"和"deadline太近所以系统排得多"。

### 决策点D4：过期提示频率——考完后弹几次？

| 选项 | 内容 | 依据 |
|------|------|------|
| **前3天每天弹1次，之后每周1次（推荐）** | 过期后前3天每天打开弹一次，3天后降为每周一评估；用户点任意按钮后立即降频/静默 | 已过期用户模拟："只弹一次不行（我考完5天没开），天天弹也不行（每天提醒我考砸了）" |
| 每天弹1次直到用户关闭 | 和方案A同样的频率机制 | 原方案C设计；但临考积压用户和已过期用户都反馈"考完了别每天戳我" |

**推荐：前3天每天弹1次，之后降频**。理由：刚过期时用户可能不在状态（考完休息几天），需要确保他回来时能看到；但一旦他知道了，就不该天天戳。
