### 1.4 实际排题上限 `getSpreadDayCap(p, date)`（app.js:2670-2687）

```js
const comfort = getComfortCap(p);
if (p.reviewMode !== 'balanced') return comfort;        // 经典：只看舒适量
if (p.dailyCapacity === 0) return comfort;               // 不自动安排
if (p.dailyCapacity != null)                              // 固定容量：min(舒适量, 固定)
  return Math.max(1, Math.min(comfort, Math.round(p.dailyCapacity)));
const cap = getDailyCapacity(p, date);
if (cap <= 0) return comfort;
if (isToday) return Math.max(comfort, cap);               // ★智能今天：max(舒适量, 智能容量)
if (p.type === 'mistake') return getMistakeDayPlan(p, date).target;
return Math.max(1, Math.min(50, cap));
```

**关键结论：**
- "min(舒适量,容量)"只在**固定容量模式**成立。
- **智能模式今天 = max(舒适量, 智能容量)**——舒适量是地板不是天花板。
- 错题未来走 `getMistakeDayPlan.target`（hardMax封顶），背书未来直接用智能容量。

## 三、舒适量智能建议死锁分析

### 3.1 算法 `getComfortAdvice(p)`（app.js:2590-2603）
- 用 `getReviewCountsByDate`（line 2482，**纯复习计数**，不含新学）。
- 14天窗口，有复习动作的天算activeDays，avg×1.2，clamp[3,15]。

### 3.2 死锁推演
```
舒适量=10 → 系统今天排max(10,智能容量) → 用户真实带宽5条
→ 每天做5条，5条变逾期，但backlog(5) < comfort(10)，不触发backlogHeavy缓解
→ getComfortAdvice: 日均复习=5，建议=5×1.2=6
→ 用户应用，舒适量=6
→ 系统排max(6,智能容量)，用户继续做5条
→ 日均=5，建议=6，永久卡死低位
```

**为什么容量算法不死锁而建议算法死锁：** 容量用 `getActivityCountsByDate`（含新学），建议用 `getReviewCountsByDate`（纯复习）。内容全部学完后，复习条数≈排题量≈舒适量，自反馈锁死。

**现有缓解（不充分）：** `renderComfortAdvice` line 2631 在 `backlog > comfort` 时不给下调建议，但死锁场景 backlog(5) < comfort(10)，不触发。

### 8.2 弹出频率机制（关键）

**不永久记住关闭，用"每天最多弹1次 + 超量才弹"控制频率：**

```
触发条件（全部满足才显示建议行）：
1. excessBanner 主模式已触发（due.length > 舒适量）
2. 智能模式（p.dailyCapacity == null）——固定模式不弹建议
3. smartCap > comfort（系统认为你能做更多，舒适量是瓶颈）
4. 当天尚未弹过（用 p.excessAdviceShownDate 记录，每天自动重置）
5. 可行性不是 risk 级别（risk时由mistakeRiskBanner引导后移deadline）

关闭行为：
- 点 [✕] 或 [知道了]：设置 p.excessAdviceShownDate = today
- 本次页面会话内不再显示（即使继续超量）
- 第二天（新的一天）重新满足条件还会再弹
- 用户点了"调高舒适量到X条"应用后，当天不再弹（因为舒适量已改，下次render时due可能不再超量或smartCap不再>comfort）
```

**为什么这样设计：**
- 不用localStorage永久记录——用户刷新后还能看到，不会永远错过。
- 每天最多1次——不会被频繁打扰。
- 只在超量+智能模式+smartCap>comfort时弹——精准定位"舒适量设低了"这一种情况。
- risk级别不弹——避免和"后移截止日"的建议冲突。

### 8.3 建议文案逻辑

```js
// 伪代码 renderExcessAdvice(p, dueCount)
function renderExcessAdvice(p, dueCount) {
  // 只服务错题、智能模式
  if (p.type !== 'mistake' || p.dailyCapacity != null) return;
  // risk级别不弹（交给mistakeRiskBanner）
  const fe = getMistakeFeasibility(p);
  if (fe.level === 'risk') return;
  // 当天已弹过不再弹
  if (p.excessAdviceShownDate === todayStr()) return;

  const comfort = getComfortCap(p);
  const smartCap = getDailyCapacity(p);

  // 情况1：smartCap > comfort（舒适量是瓶颈）
  if (smartCap > comfort && smartCap > defaultComfortCap(p)) {
    const suggest = Math.min(smartCap, 20);  // 硬上限20
    el.innerHTML = `
      💡 你的学习节奏显示每天能处理约 <b>${suggest}</b> 条，
         当前舒适量 ${comfort} 条偏保守。调高后系统会排得更满、减少堆积。
      <button onclick="applyAdvice(${suggest})">调高舒适量到 ${suggest} 条</button>
      <button onclick="dismissAdvice()">✕</button>`;
    el.hidden = false;
  }
  // 情况2：smartCap ≤ comfort（舒适量不是瓶颈，是历史积压）
  else {
    el.innerHTML = `💡 系统评估你每天适合约 ${smartCap} 条，当前舒适量 ${comfort} 条已足够。
                    今天的超额是历史积压，稳步清完即可。
                    <button onclick="dismissAdvice()">✕</button>`;
    el.hidden = false;
  }
}
```

### 8.4 "一键应用"行为
- 只改 `p.spreadThreshold = suggest`，**不改容量**（智能模式容量由系统自动算）。
- 立即 `saveStore()` + `render()`。
- 应用后 `p.excessAdviceShownDate = today`，当天不再弹。
- **下限保护**：建议值不低于默认值（错题10）。代码中 `Math.max(defaultComfortCap(p), Math.min(smartCap, 20))`。

### 8.5 为什么用"smartCap差距"替代"日均完成量"
- smartCap 用 EWMA（半衰期14天，含新学动作），对短期偷懒有平滑效果。
- smartCap 受 deadline均摊兜底——临近考试时不会因近期做得少而建议调低。
- smartCap 不受舒适量锁死（它是独立计算的）。

```
1. p.deadline 存在

3. 项目内还有未掌握条目（getDueItems + 未mastered的总数 > 0）

- 用户修改了截止日（改到未来）后，自然不再弹
```

### 9.3 过期分级文案

| 过期程度 | 条件 | 主文案 | sub文案 |
|---------|------|--------|---------|
| 刚过期 | 0 < daysPassed ≤ 3 | 📌 目标日已过 {N} 天，还有 **{M}** 条未完成 | 系统已切换为纯间隔复习节奏。[修改截止日] [本次关闭] |

2. **「本次关闭」** → 记录今天已关闭，当天不再弹。

### 9.5 必须配套修复的BUG
**scheduleNextReview 过期clamp修复（app.js:3132, 3135）：**
```js
// 修复前：
```

## A. 间隔重复 scheduleNextReview 完整算法

**位置：app.js:3075-3137。**

### A.1 基础间隔

- 间隔表 `getIntervals(p)`（line 1616）：默认 `[1,2,4,7,15,30]`，共6轮，累计59天毕业。
- 单题可覆盖：`getItemIntervals(item,p)`（line 3404）优先取 `item.customIntervals`。
- 评价三档模型 `transitionReview`（line 3413）：
  - good：进入下一轮，间隔=下一档标准间隔。
  - fuzzy：进下一轮但间隔×1.3封顶（不快速放到长间隔）。
  - forgot：停留本轮，间隔回首轮；连续2次forgot退一轮。

### A.2 错峰（仅 balanced 模式）

- 窗口：`maxForward = gap×0.25`，`maxBack = min(2, gap×0.25)`（line 3121-3122）。
- 早期复习（间隔≤2天）`maxExtend=3`；后期 `maxExtend=14`（line 3125）。
- 调用 `findAvailableDate`（line 3017）：在窗口内找 load/cap 比最低的日子，并列取最近；窗口全满则向后扩展 maxExtend 天找空位。

### A.3 背书冲刺期特殊逻辑（line 3088-3107）

仅 `p.type==='recite' && p.deadline && d2d>=0 && d2d<=cycleDays` 时进入：
- 任何复习不排到考试之后。
- fuzzy/forgot 内容考前2-3天必再见（`capGap = min(3, d2d)`）。
- 最后7天（sprintTail）：全窗口负载均衡，不堆到目标日。
- 非good内容若下次到期≥目标日，标记 `finalReviewDate` 并把下次排到 deadline+1（考前最后一遍）。

### A.4 过期后 clamp BUG 详细分析

**问题代码（line 3132, 3135）：**
```js
if (p.deadline && d > p.deadline) d = p.deadline;        // balanced
if (p.deadline && base > p.deadline) return p.deadline;   // classic
```

**触发链（用户模拟已过期用户实测验证）：**
1. 截止日=2026-09-30（已过期5天）。
2. 用户今天复习一道题，评价good，应排到 today+7=2026-10-12。
3. 错峰后 d=2026-10-12 > deadline=2026-09-30 → clamp 到 2026-09-30。
4. 这道题 nextReviewDate=2026-09-30（过去）→ 立即出现在今天的逾期列表。
5. 用户又做一遍 → 又被 clamp 到 2026-09-30 → 无限循环。

**用户原话（已过期用户模拟）：** "我明明刚点了'做对了'，系统不是说下次7天后吗？怎么今天又出现在逾期列表里？我连续做了三道，三道全回来了。"

**修复方案：** clamp 前加 `p.deadline >= todayStr()` 条件，过期后不再 clamp。

## B. 按期均摊 getDeadlineLevelCap

**位置：app.js:2526-2576。**

### B.1 输入与输出
- 输入：项目 p，日期 date。
- 输出：`{ cap, need, studyDaysLeft, newCap, reviewCap }`。
- cap = ceil(reviewCap + newCap)，是智能容量的硬下限之一。

### B.2 计算逻辑
1. **早退条件**（line 2530-2533）：非recite/mistake、无deadline、daysLeft≤0或>120 → cap=0。
2. **复习需求 reviewNeed**（line 2539-2549）：遍历所有未掌握、未finalReview的条目，按 `剩余轮次 = totalStages - stage` 累加。
3. **新学需求 newCap**（line 2552-2572）：仅背书类型，在 `deadline - cycleDays` 之前的窗口内，把未学页均摊到学习日。错题不做新学均摊。
4. **studyDaysLeft** = daysLeft × getStudyDayRatio（学习日比例）。

### B.3 过期后 return 的影响
- deadline≤today → daysLeft≤0 → return cap=0。
- 这意味着 `getDailyCapacity` 中的"按期均摊硬下限"（line 2747-2748）在过期后不再拉高容量。
- 智能容量退化为只剩 EWMA速率 ∨ 积压追赶 ∨ 星期画像。
- **积压追赶仍生效**（line 2740-2743），所以过期后如果还有逾期，backlog仍会拉高容量——但 getMistakeDayPlan.target 又把它压到 min(hardMax, raw)。

## E. 可行性警告 getMistakeFeasibility 与其他算法的交互

**位置：app.js:3264-3285。**

### E.1 数据来源
- `remainRounds`：每条未掌握题剩余轮次之和（line 3272-3276）。
- `predictedNew`：`getMistakeCollectRate`（line 3231，近28天收录速率）× 剩余天数（line 3277）。
- `work = remainRounds + predictedNew`。

### E.2 判定阈值
- comfort = getComfortCap(p)。
- hardMax = min(20, max(12, comfort×1.5))。
- work > studyDays×hardMax → risk；work > studyDays×comfort → tight。

### E.3 与排期算法的关系
- **getMistakeDayPlan.hardMax 用同一公式**（line 3257），保持一致。
- **但 feasibility 不读 EWMA 实际速率**（用户模拟痛点4）：高强度用户实际能做18条，feasibility仍按comfort=10算，容易误报risk。
- **今天排题和未来排题口径不一致**（用户模拟痛点7）：
  - 今天：getSpreadDayCap = max(comfort, getDailyCapacity)，getDailyCapacity取deadline均摊23 → 今天排23。
  - 未来：getMistakeDayPlan.target = min(hardMax=15, raw=23) = 15。
  - 结果：今天塞23条，中期每天只15条，每天落后8条，考前爆量。

## F. 新题收录速度预测 & 剩余轮次计算

### F.1 getMistakeCollectRate（app.js:3231-3239）
- 取所有 learnedDate，近28天有≥2条则用 recent/28。

### G.1 模式定义

## H. 逾期分散 spreadItems 完整逻辑

**位置：app.js:2324-2393。**

### H.1 防饥饿规则 canBeSpread（line 3387-3396）
- spreadCount≥3 → 不能再推。
- 逾期天数 > 当前间隔×2 → 不能再推。
- nextReviewDate为空 → 不能再推。

### H.2 分散算法
1. 锁死条目强制回今天（line 2333-2335）。
2. 未来days天建立负载表，每天cap=getSpreadDayCap（line 2361）。
3. 按优先级（compareItemPriority）逐条分配：
   - 第一轮：找 load/cap 比最低且未满的日子，并列取最近。
   - 第二轮：窗口全满时，选绝对负载最低、并列取最远（保护近期）。
4. 每条 spreadCount++，lastSpreadDate=today。

### H.3 与舒适量的关系
- 每日上限 = `getSpreadDayCap(p, date)`（line 2361）。
- classic/容量0模式下 = 舒适量。
- balanced智能模式下 = getDailyCapacity（可超舒适量）。
- 所以分散的上限不是固定等于舒适量，而是取决于当天算出来的排期上限。

### H.4 两个入口
- `spreadOverdueItems`（line 2301）：overdueBanner按钮，保留今天到期的，分散逾期超额。
- `spreadExcessToday`（line 2399）：excessBanner按钮，保留舒适量内（或当前一半）在今天，其余分散。

## I. 各算法交互关系图

```
用户复习评价（good/fuzzy/forgot）
  │
  ├─→ transitionReview：算新stage/gap
  │
  └─→ scheduleNextReview(p,item,today,stage,gap)
        │
        ├─ classic模式：严格返回 today+gap（过期后BUG：clamp到过去deadline）
        │
        └─ balanced模式：
              │
              ├─ findAvailableDate：在gap×0.25窗口找最空日
              │     （每日cap = getDailyCapacity(p,d)）
              │
              └─ deadline clamp（过期后仍执行=BUG）
                    │
                    ▼
              item.nextReviewDate = d


每日打开项目时（renderReview前）：
  │
  ├─ ensureAtLeastOneReview（错题+未来deadline）：stage=0的题兜底排到deadline前
  │
  ├─ pullForwardIfNeeded（错题+balanced+未来deadline）：
  │     今日due < getMistakeDayPlan.target → 从未来14天拉薄弱题到今天
  │
  ├─ autoBalanceIfNeeded（balanced）：
  │     due > getSpreadDayCap(today) → 超额的走spreadItems摊到未来
  │
  └─ settleToday（错题）：达标后把误提前的顺延回明天


容量计算链：
  getDailyCapacity(p,date)
    = max(
        EWMA速率（含新学动作）,
        getBacklogCatchUp.need（积压追赶）,
        getDeadlineLevelCap.cap（按期均摊）,
        getWeekdayAwareCap（星期画像，只上抬）
      )
    clamp [1,50]

  getSpreadDayCap(p,date)
    = classic: 舒适量
    = balanced+固定: min(舒适量, 固定容量)
    = balanced+智能+今天: max(舒适量, getDailyCapacity)
    = balanced+智能+未来+错题: getMistakeDayPlan.target
    = balanced+智能+未来+背书: getDailyCapacity（可超舒适量）


提示系统：
  overdueBanner：getOverdueItems.length > 0
  excessBanner：due.length > 舒适量（不看容量）
  mistakeRiskBanner：getMistakeFeasibility.level === 'risk'
  deadlinePassedBanner：（待实现）deadline < today 且有未完成
```
