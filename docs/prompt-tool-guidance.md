# Function Calling 系统 Prompt 引导段设计

> 对应文件：`backend/utils/aiPrompt.js`，`buildSystemPrompt(profile, memories)`
> 目的：在系统 Prompt 中加入一段引导，告诉 AI 什么时候该调用只读工具查数据、什么时候直接回答、怎么控制调用成本。
> 语气要求：与现有 Prompt 一致——专业、客观、自然，不写冷冰冰的指令列表。

---

## 一、工具使用引导段（可直接插入系统 Prompt）

以下文本约 420 字，与现有 Prompt 同款【】小节标题 + 自然段落风格，可直接拼进 `buildSystemPrompt` 返回字符串。建议插入位置见第二节。

```
【怎么查他的数据】
你手里有一组只读查询工具，可以主动调用去查他的学习数据——今天的待办、某个项目的进度、近一周的统计、错题薄弱点这些。他一旦问到具体数字或具体情况，比如"今天该学什么""我高数错题本怎么样了""最近一周学了多少"，你先从手边的查询工具里挑最合适的那个，拿到真实数据再开口，别凭印象编，也别拿上一轮的旧答案硬套。反过来，纯方法论、学习方法建议、心态上的鼓励、考研常识，这些不依赖他数据的问题，直接答，不用调工具。

调之前想清楚：一个工具能说清的别调两个；问"今天做什么"就直接查今日待办，不用先翻项目列表。可以连续调多个（比如先列一下他有哪些项目，找到他说的那个错题本，再查它详情），但一轮对话里最多调 5 次，拿到够用的数据就停。上一轮刚查过、他又问同样的事、数据不可能变，就直接接着说，别重复调。工具返回的内容是给你看的，用自己的话转述给他，别把 JSON 贴出来。调失败了就告诉他暂时查不到，然后基于一般情况给建议。记住这些调用都走他自己的 API Key，每多调一次就多花他一份 token，别为了"显得严谨"滥调。
```

### 设计要点逐条对应需求

| 需求点 | 在引导段中的落点 |
|---|---|
| 什么时候必须调工具 | "他一旦问到具体数字或具体情况……先调工具拿到真实数据再开口，别凭印象编" |
| 什么时候直接回答 | "纯方法论、学习方法建议、心态上的鼓励、考研常识……直接答，不用调工具" |
| 多轮调用策略 | "可以连续调多个……但一轮对话里最多调 5 次，拿到够用的数据就停" |
| 效率原则 | "一个工具能说清的别调两个"；"上一轮刚查过……别重复调" |
| 结果呈现 | "用自己的话转述给他，别把 JSON 贴出来" |
| 工具失败处理 | "调失败了就告诉他暂时查不到，然后基于一般情况给建议" |
| 成本控制 | "走他自己的 API Key，每多调一次就多花他一份 token，别为了'显得严谨'滥调" |

## 二、系统 Prompt 改造方案

### 2.1 `<learning_data>` 全量注入怎么处理

现状：`buildSystemPrompt` 里硬编码了 `<learning_data>{data_json}</learning_data>` 占位（实际由 `buildUserPrompt` 在每轮注入聚合数据），属于**每轮全量塞进上下文**。这在 Function Calling 模式下有两个问题：

1. 全量数据本身就要吃一大段 input token，和"按需查工具"的设计冗余；
2. 数据一直在上下文里，AI 反而可能偷懒不调工具、直接拿旧数据答，失去实时性。

**建议改造（双模式）：**

- **Function Calling 模式（默认）**：
  - 系统 Prompt 中**不再注入** `<learning_data>` 全量块；
  - 保留轻量画像（`【他的情况】`，即现有 `profileLine`）和长期记忆（`【你记得的事】`）——这些是 AI 自我介绍时需要的静态信息，量小；
  - 把上面的【怎么查他的数据】引导段插进去，让 AI 知道"数据要自己去查"。
- **降级模式（模型不支持 function calling，如某些旧版 OpenAI 兼容接口）**：
  - 恢复现状：保留 `<learning_data>` 全量注入；
  - **不要**插入【怎么查他的数据】引导段（没有工具可调，引导段反而误导）。

### 2.2 引导段在 Prompt 中的位置建议

现有顺序：

```
角色定义 + 日期
【这个系统是干什么的】
【你所在的系统是怎么工作的】
【你的说话方式】
【话题边界】
【他的情况】
【你记得的事】
【他的真实数据】<learning_data>…</learning_data>
【回复格式】
```

建议调整后（FC 模式）：

```
角色定义 + 日期时间行（见 2.4）
【这个系统是干什么的】
【你所在的系统是怎么工作的】
【怎么查他的数据】          ← 新增，插在这里
【你的说话方式】
【话题边界】
【他的情况】                ← 保留，轻量画像
【你记得的事】              ← 保留，长期记忆
（删掉【他的真实数据】整段）
【回复格式】                ← 保留，actions 块契约不变
```

**为什么放在"系统怎么工作"之后、"说话方式"之前：**
- AI 先理解系统是什么、数据模型长什么样（前两节），才能理解"查工具"查的是什么；
- 工具调用本质上是一种行为规范，紧接着说话方式一起看，行为约束成组出现，不零散；
- 放在数据区附近会让人误以为"数据就在这里"，和 FC 模式"数据要现查"的设定矛盾。

### 2.3 需要做的最小代码改动

`buildSystemPrompt(profile, memories)` 签名加一个参数：

```js
function buildSystemPrompt(profile, memories, options = {}) {
  const { enableTools = false } = options;  // true = FC 模式，false = 降级全量注入
  // ...
}
```

然后在模板里做条件拼接：

- `enableTools === true`：
  - 插入【怎么查他的数据】段；
  - 删除/留空【他的真实数据】整段（含 `<learning_data>` 占位）；
- `enableTools === false`：
  - 保持现状，全量注入 `<learning_data>`，不插入工具引导段。

`buildUserPrompt` 同步调整：FC 模式下不再往里塞 `<learning_data>`（工具结果会以 tool message 形式回到上下文，不需要再在 user message 里重复）；降级模式保持现状。

**actions 块契约完全不动**：修改类操作目前只有 `adjust_daily_comfort`（调整舒适量），仍然走回复末尾的 ```actions``` 块 + 用户点"应用"确认，AI 不通过 function calling 执行任何写操作。后续不会通过 function calling 新增修改/创建类工具——所有写操作都维持"AI 提建议、用户确认"的模式。这一点引导段里没展开，现有【回复格式】段已经讲清楚了，不需要重复。

### 2.4 当前时间注入（不做工具，直接写进系统 Prompt）

AI 需要知道"现在几点"才能做这类判断：晚上 10 点后建议收工别排新任务、早上建议先啃最难的科目、用户问"今天还能学多久"时算一下剩余时间。

**结论：不要单独做 `get_current_time` 工具，直接在系统 Prompt 里注入时间更省 token。** 每次工具调用都是一轮额外的 LLM round-trip，而时间是每轮请求后端本来就能拿到的——直接写进 Prompt，零额外开销。

**注入格式**（替换现有"今天是 …，距考研还有 … 天"那一行）：

```
今天是 2026-10-06，现在是 15:30（北京时间，UTC+8），距 2027 年 12 月 19 日考研初试还有 439 天。
```

紧接着补一句行为提示（告诉 AI 这个时间能用来干嘛，不用它自己悟）：

```
你可以用这个时间判断早晚：晚上 10 点后就别再建议排新任务，提醒他收工睡觉；早上状态好的时候，可以建议先啃最难的科目；他问"今天还能学多久"时，按他平时的作息算一下剩余时间，别把任务排到半夜。
```

**后端注意**：
- 服务器可能跑在 UTC 时区，**后端必须在拼这一行时显式转成北京时间（UTC+8）**，不能直接 `new Date()` 取服务器本地时间——否则部署到云上服务器会差 8 小时；
- 时间串由后端每次请求动态生成，不要硬编码；
- 降级模式下同样注入这一行（时间不依赖 function calling，两种模式都该有）。

## 三、工具调用示例

> 说明：下面示例里出现的工具名（`get_today_tasks`、`get_projects_summary` 等）只是示意。实际上线时查询类工具集可能扩充，AI 应以请求里下发的 tool schema 为准，**根据用户问题挑语义最匹配的那个查询工具**，不要被这里列死的名字绑住。引导段本身不写死工具名，就是为了留这个扩展空间。

### 场景 A：用户问"我今天要做什么"

**用户消息**：`"我今天要做什么"`

**AI 判断**：这是典型的"问具体数据"——今天的待复习/待新学任务，必须实时查，不能凭印象。

**工具调用**：直接调 `get_today_tasks`。不需要先列项目（用户问的是"今天"，不是"某个项目"）。

**拿到结果后**：用自然语言转述，不贴 JSON。例如：

> 今天排了 3 件事：高数错题本有 5 道到期复习（其中 2 道是上次看错答案的，优先看），英语单词新学 20 个 + 复习旧词 15 个，政治刷题本按节奏走 3 页。按你每天 2 小时算，错题大概 40 分钟、单词 30 分钟、政治 30 分钟，留点缓冲。错题那 2 道上次错的先拿出来过一遍，别一上来就刷新题。

### 场景 B：用户问"数学怎么学"

**用户消息**：`"数学怎么学才能不遗忘"`

**AI 判断**：纯方法论问题，不依赖用户具体数据。哪怕系统里有他的错题记录，这种问题问的是通用方法，直接答即可。

**工具调用**：不调。

**回复示例**：

> 数学不遗忘的关键不是刷更多题，而是"做错的题按时回头看"。一道题错了，当天搞懂，第 2 天、第 4 天、第 7 天各翻一次，每次只问自己"这一步为什么这么想"，不用整题重做。连续三次都能讲清楚思路，这道题就真的是你的了。你现在错题本的间隔表就是按这个节奏排的——关键是别跳复习日，攒着一起看效果会差很多。

> （最后一句轻轻点一下他系统里的机制，但没有调工具，只是基于 Prompt 里"系统怎么工作"那段已知信息。）

### 场景 C：用户问"我那个高数错题本现在怎么样了"

**用户消息**：`"我那个高数错题本现在怎么样了"`

**AI 判断**：问具体项目的数据，但用户只说了"高数错题本"，没给 projectId。第一步必须先找到这个项目是哪个。

**第一轮工具调用**：`get_projects_summary`（列出所有项目，找到名字带"高数/错题"的那一项，拿到 projectId）。

**第二轮工具调用**：`get_project_detail(projectId=...)`（拿这条错题本的条目数、掌握情况、近期复习记录）。

**两轮拿到结果后**：组织回复。例如：

> 你那个"高数错题本"目前一共 47 道题：已经攻克的 21 道，正在复习中的 18 道，还有 8 道是新收进来没开始走间隔的。最近 7 天到期复习 12 道，你完成了 9 道，完成率 75%——漏的那 3 道是周三、周四的，已经自动摊到后面几天了。薄弱点集中在极限和中值定理那两章，占了未攻克题的一半。建议这两天把摊过来的补一下，别让它继续往后滚。

**如果用户下一句追问"那极限那块具体哪几道"**：可以再调一次 `get_mistake_analysis` 或 `get_project_detail` 拿到章节细分，但如果上一轮 `get_project_detail` 已经返回了按章节的薄弱点统计，就直接引用，不再调。

## 四、成本控制提示词（已内嵌在引导段中）

引导段最后一句是专门为成本控制写的，单独拎出来强调：

> "记住这些调用都走他自己的 API Key，每多调一次就多花他一份 token，别为了'显得严谨'滥调。"

为什么要把这句话写进给 AI 的 Prompt 而不是写在后端代码里：

1. AI 自己不知道每次 tool round-trip 都要额外消耗 input+output token（它只看到自己在"调工具"）；明确告诉它"这是用户自己掏钱"，它才会有节流意识；
2. 比单纯写"请节约调用"更有说服力——绑定到"用户的 API Key"这个具体利害关系上，比抽象的"节约 token"更能改变行为；
3. 配合前面"一个工具能说清的别调两个""上一轮刚查过别重复调""最多 5 次"这几条，形成"动机（别花用户钱）+ 规则（几条具体动作）+ 上限（5 次）"的三层约束。

后端侧建议再加一道兜底（不在 Prompt 里，在代码里）：单次对话对 AI 的 tool_call 轮次做硬上限（比如 6 轮），超过就强制让它基于已有信息回答，防止极端情况下 AI 陷入"调一个→不够→再调一个→还不够"的循环烧 token。
